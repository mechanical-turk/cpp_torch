# Short 07: Focused script critique, September 7

Scope: one critique/rewrite of the existing false-sharing script, followed by
a second review. Sequential writer/critic passes, not independent reviewers.
Canonical revision and S01-S20 plan/audit: [script.md](script.md).

## First review: specific weaknesses

| Earlier wording | Viewer problem | Applied repair |
| --- | --- | --- |
| Wasting memory made this faster. | "This" leaves the actual subject entirely to the diagram. | Keep the high-signal opening, but name "these threads." |
| Their writes keep taking ownership of the same line from each other... | Names ownership without stating why different counters need the same thing. | State the whole-line write-access rule before its consequence. |
| Move b into a separate cache line. | Shows relocation but does not name how the empty memory belongs to the implementation. | "Add padding so b starts on another cache line." Match the unused slots to "padding." |
| Now they can update without taking that line from each other. | Repeats the previous mechanism in a long negative sentence. | "That stops the back-and-forth." The stable rim colors show what stops. |
| Same work, [N] times faster. | Work and scope remain vague. | "Same updates, [N] times faster in this test." Keep the ratio a placeholder. |
| Could local counters beat both? | A new technical term arrives just before the cut, without a concrete next action. | "What if we only shared the final totals?" Same proposed direction, described behaviorally. |

## Lesson applied

Use the extra duration to teach a causal rule, not to add more terminology.
Name the proposed next experiment as a change the viewer can picture. Existing
S04-S06, S10, S14, and S16 cover these repairs; no new global rule is needed.

The prior false-sharing pitch lab already warned about prerequisite load. This
pass addresses that warning by explaining the visible boundary's significance,
not by deleting the explanation to achieve a smaller word count.

## Second review of the revision

- Hook remains assertive and result-led. It names threads without adding setup
  before "Wasting memory." Do not replace it with a neutral definition.
- Explanation now proceeds in dependency order: different counters, shared line,
  whole-line write access, interference, padding. Each sentence has a visual cue.
- The mechanism is simplified, not a lock model. Keep counter stalls schematic;
  do not freeze the processors or depict mandatory alternation per increment.
- Same updates and test-specific wording make the comparison clear. Timing
  verification stays with production and is not deducted from the script score.
- Result is followed immediately by the why-question. The second question names
  final-only publication and gives a concrete reason to return.
- The primary remaining editorial risk is spoken pacing across the two-question
  outro. Preserve its distinct beats rather than delivering it as a checklist.
  The planned eight-second window is not proof of an actual timed performance.
- Sharing final totals changes intermediate visibility. Production notes retain
  that limitation; the short does not falsely declare it an equivalent winner.
